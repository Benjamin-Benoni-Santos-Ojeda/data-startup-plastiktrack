E3 · Arquitectura de Microservicios y Contenedores

1. Justificación del Desacoplamiento (Microservicios vs Monolito)

En las fases E1 y E2, el motor analítico residía acoplado en un entorno de experimentación. Para garantizar escalabilidad operativa, disponibilidad continua y aislamiento de fallas, la arquitectura se divide en tres microservicios independientes comunicados mediante HTTP REST fuertemente tipado bajo contratos Pydantic v2.

Microservicio Tecnología Base Directorio Puerto Responsabilidad Operativa
API Inferencia IA FastAPI + scikit-learn services/modelos/ 8000 Inferencia de demanda, backtesting y cálculo de compra sugerida a 14 días con stock de seguridad (95%).
Dashboard Ejecutivo Streamlit + Plotly services/tablero/ 8501 Visualización de 4 KPIs, series temporales, matrices de correlación y visualización de inventarios.
Worker / Ingesta Python Batch Engine services/worker/ N/A Ingesta periódica de ventas, validación de integridad y reentrenamiento programado de modelos.

Contenerización Docker y Orquestación Local

4. Especificación de Dockerfiles y Optimización de Imágenes

Se implementaron Dockerfiles específicos para cada microservicio. A continuación se presentan los fragmentos clave de la API de inferencia (services/modelos/Dockerfile) y la composición multi-contenedor (docker-compose.yml):

# services/modelos/Dockerfile (API Inferencia FastAPI) FROM python:3.12-slim AS base WORKDIR /app RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/* COPY requirements.txt /app/requirements.txt RUN pip install --no-cache-dir --upgrade pip && pip install --no-cache-dir -r requirements.txt COPY services/modelos/modelo_demanda.joblib /app/services/modelos/modelo_demanda.joblib COPY services/modelos/api.py /app/services/modelos/api.py RUN useradd -m -u 1001 appuser && chown -R appuser:appuser /app USER appuser EXPOSE 8000 HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost:8000/health || exit 1 CMD ["python", "-m", "uvicorn", "services.modelos.api:app", "--host", "0.0.0.0", "--port", "8000"]

5. Orquestación Local Multicontenedor (docker-compose.yml)

version: '3.8' services: api-modelos: build: { context: ., dockerfile: services/modelos/Dockerfile } ports: ["8000:8000"] networks: [plastiktrack-net] healthcheck: { test: ["CMD", "curl", "-f", "http://localhost:8000/health"], interval: 30s } deploy: { resources: { limits: { cpus: '1.0', memory: 512M } } } tablero: build: { context: ., dockerfile: services/tablero/Dockerfile } ports: ["8501:8501"] depends_on: { api-modelos: { condition: service_healthy } } networks: [plastiktrack-net] networks: plastiktrack-net: { driver: bridge }
Garantía de Resiliencia: La directiva depends_on con condición service_healthy impide que el dashboard de Streamlit inicie antes de que el modelo de Machine Learning esté completamente cargado en memoria y respondiendo en /health.

Orquestación en Kubernetes: Despliegue y Recursos

6. Manifiestos Declarativos en Namespace Dedicado

Para entornos de clúster gestionado o K3s, los manifiestos en k8s/ establecen la configuración declarativa de alta disponibilidad:

Manifiesto Objeto Kubernetes Configuración Crítica Propósito Operativo
00-namespace.yaml Namespace name: plastiktrack Aislamiento lógico, gobernanza y cuotas de consumo por proyecto.
01-configmap.yaml ConfigMap API_URL, OCI_REGION, BUCKET Inyección de parámetros sin necesidad de recompilar imágenes de Docker.
02-api-deployment.yaml Deployment 2 réplicas, RollingUpdate (0 unavail) Despliegue del motor de IA con actualización continua sin caída de servicio.
03-api-service.yaml Service ClusterIP:8000 Balanceo de carga interno round-robin hacia los pods sanos de la API.
04-tablero-deployment.yaml Deployment 1 réplica, probes /_stcore/health Despliegue del dashboard Streamlit con asignación de 256Mi a 512Mi.
05-tablero-service.yaml Service ClusterIP:8501 Punto de acceso interno para el tablero gerencial.

7. Estrategia de Sondas de Salud (Liveness y Readiness Probes)

Se desacoplaron las sondas para asegurar que ningún cliente reciba errores 502/503:

  • Readiness Probe: Consulta /health cada 10s tras 10s de arranque inicial. Si el modelo aún no termina de deserializar modelo_demanda.joblib, el pod no recibe tráfico de la red.
  • Liveness Probe: Verifica la vitalidad del proceso cada 20s. Si el servidor ASGI se bloquea, Kubernetes reinicia automáticamente el pod afectado.

Ruteo con Ingress y Autoescalado (HPA)

8. Enrutamiento HTTP Unificado (Ingress NGINX)

Mediante k8s/06-ingress.yaml, un único punto de entrada HTTP enruta el tráfico entrante según la ruta solicitada: la raíz / se despacha hacia el tablero-service:8501, mientras que /api/v1, /docs y /health se dirigen hacia el api-service:8000.

Figura 3: Topología del clúster Kubernetes. El Ingress distribuye peticiones externas hacia los ClusterIP services y el HPA monitorea el consumo de CPU de la API de inferencia.

9. Elasticidad con Horizontal Pod Autoscaler (HPA)

Para absorber picos de tráfico durante los cierres de quincena (+28% en demanda demostrada en E2), el manifiesto k8s/07-hpa.yaml ajusta automáticamente el número de réplicas de la API de inferencia entre 2 y 6 pods al superar el 70% de consumo promedio de CPU:

# k8s/07-hpa.yaml (Autoescalador elástico de la API de IA) apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: { name: api-modelos-hpa, namespace: plastiktrack } spec: scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api-modelos-deployment } minReplicas: 2 maxReplicas: 6 metrics: - type: Resource resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

Especificación y Contratos de la API REST

10. Endpoints Oficiales de Inferencia (services/modelos/api.py)

La API REST expone de manera segura y tipada los algoritmos de pronóstico y optimización logística desarrollados en E2:

Método Ruta Esquema Entrada Esquema Salida Descripción y Métricas
GET /health Ninguno HealthResponse Estado del servicio, uptime, versión v1.0.0, WAPE 12.29%, MAE 3.79 y latencia.
GET /api/v1/skus Ninguno List[SKUInfo] Catálogo de los 12 productos plásticos, familias y precios vigentes.
POST /api/v1/predict PredictRequest PredictResponse Predicción de demanda por SKU y fecha evaluando quincenas y días de reparto.
POST /api/v1/replenish ReplenishRequest ReplenishResponse Cálculo de compras a 14 días con stock de seguridad (95% nivel de servicio, Z=1.65).
GET /metrics Ninguno text/plain Métricas compatibles con Prometheus (uptime, WAPE, MAE y RMSE).

11. Motor de Decisión de Compras a 14 Días

El endpoint /api/v1/replenish ejecuta la lógica analítica de cadena de suministro sobre los 12 SKUs:

$$\text{Stock de Seguridad} = Z \times \sigma_{\text{error}} \times \sqrt{14} \quad (Z = 1.65 \implies 95\% \text{ de nivel de servicio})$$

$$\text{Pedido Sugerido} = \max(0, \text{Pronóstico a 14 días} + \text{Stock de Seguridad} - \text{Inventario Actual})$$

Resultado de Inferencia: Para un inventario en cero, el motor recomienda un aprovisionamiento total de 5,498 bultos/cajas equivalentes a una inversión total de $232,548.00 MXN, mitigando el quiebre de stock en el producto líder (Bolsa Negra Camiseta, 728 unidades sugeridas).

13. Cumplimiento de OWASP API Security Top 10

  • API1 (Broken Object Level Authorization): Filtrado estricto por SKU validado contra el catálogo oficial en memoria.
  • API3 (Broken Object Property Level Authorization): Esquemas Pydantic con rechazo estricto de campos no declarados.
  • API4 (Unrestricted Resource Consumption): Sondas de timeout (2-5s) y límites estrictos de CPU y memoria en Kubernetes.
